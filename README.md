# JCOE 공정 시뮬레이터

세아제강 포항공장 JCOE 강관 생산 라인의 **공정 흐름 시뮬레이터**입니다.
POSTECH 산업경영공학과 IDEA Lab × 세아제강 「철강 제조 공정의 실시간 대응을 위한 지능형 시스템 개발」 과제 산출물.

공정 다이어그램의 실제 흐름을 그대로 재현하고, 표준시간 산출식 엑셀(SMART기술팀, 2025-12-18)의
20개 공정 계산식을 브라우저에서 재계산합니다. 확관기 배분 규칙과 최적화 엔진을 포함합니다.
확관 제약의 **정본은 확관 최적화 운영 모델 `specs.py`** 입니다 (2026-08-06 세아제강 확정).

### 3D 공장 탭

2D 와 **완전히 같은 계산 결과**를 입체 공장 화면으로 봅니다 (계산은 2D 에서 한 번만 합니다).
기준정보·계획서·설정을 바꾸면 3D 도 즉시 따라옵니다.

**3D 전용 레이아웃**입니다. 2D 도면을 그대로 투영하면 설비 간격이 좁아 어느 공정 앞에 물량이 걸렸는지
읽기 어려워서, 흐름을 좌 → 우 로 통일하고 행(aisle)을 넉넉히 벌린 배치로 다시 설계했습니다.

```
조관 12M 라인        E/M → Pre Bender → Press Bender
조관 18M 라인        E/M → Pre Bender → Press Bender      ─┬→ 두께 25T 분기 → Gap Press
용접 · 절단 (SAW)    태그 웰딩 → 내면 SAW ×4 → 슬러그 제거 → 외면 SAW ×4 → 관단탭 절단 → 1차 U.T
확관 (병목 공정)     10번 문 Buffer → RB 라인 / 확관 #1·#2호기 → CP → 면취기 → 수압
검사 · 출하          Final U.T → 관단 X-ray → F-X ray ×2 → 포장 및 출하
보수 · 재작업        Repair → 보수 용접 / Expander 문제
```

**공정별 전용 적치장(bay)** — 각 설비 앞에 바닥이 칠해진 적치 구역을 두고, 대기 자재를 그 안에만 쌓습니다.
구역 색이 대기량에 따라 초록 → 파랑 → 노랑 → 빨강으로 바뀌고, 옆에 **WIP 게이지 막대**가 서 있어
멀리서도 어느 공정 앞에 물량이 걸렸는지 한눈에 보입니다. 적치장 앞에는 `대기 27` 같은 수량 배지가 붙습니다.

- **설비 형상** — 밀링 베드, 프레스 갠트리, 용접 토치·와이어릴, 확관기 드로바, 수압 압력용기, X-ray 포털, 포장 밴딩 스테이션을 공정별로 구분
- **자재 흐름** — 후판(판재) → U/O 성형 반제품 → 강관으로 형상이 바뀌며, 각 설비 앞에 대기 자재가 실제로 쌓입니다. 확관 대기분은 10번 문 Buffer 랙에 적치
- **야드** — 원자재(후판) 야드는 줄고 완제품 야드는 늘어납니다. 완주 시 후판 0매 / 완제품 1,446본
- **호기 분리** — 확관 #1·#2호기, 내면·외면 SAW 4라인, F-X ray 2대가 물리적으로 분리된 설비로 표시
- **조작** — 좌 드래그 회전 / 우 드래그(또는 Shift) 이동 / 휠 확대 / 설비 클릭 시 가동률·전환시간·산출식
- **재생** — 타임라인 슬라이더로 임의 시점 점프·되감기, 반복 재생, 변동성 토글, 🎲 새 시드 재실행

### 기준정보 탭 — 현장에서 코드 없이 숫자 고치기

표준시간 상수가 종전에는 `engine.js` 함수 **안에 숫자로 박혀** 있어서, 값 하나를 고치려면
코드를 열고 `build.py` 를 다시 돌려야 했습니다. 현장에서는 사실상 불가능한 절차였습니다.

이제 전부 **기준정보(REF)** 로 빠져 있고, 시뮬레이터 「기준정보」 탭에서 직접 고칩니다.

| 서브탭 | 고칠 수 있는 것 | 항목 수 |
|---|---|---|
| **설비 대수** | 공정별 설비 대수 (확관은 설정 탭에서 지정) | 28 |
| **전환시간** | 공정별 외경/두께/길이 변경 시 전환시간 [초] | 15공정 × 3 |
| **표준시간 상수** | 산출식의 모든 상수 — 기본시간·분모·계수·확관 Step 여유·셋업 시간 | 15공정 · 78항목 |
| **룩업 표** | 엑셀에서 뽑아 온 구간 표 (보기 전용) | 15표 |

#### 쓰는 법

1. 값을 고치면 **즉시 다시 계산**됩니다. 위쪽에 `완료까지 / 1위 병목 / 원래 대비 ±일` 이 바로 바뀝니다.
2. 원본과 다른 칸은 **노란색**으로 표시되고 옆에 **되돌리기(↺)** 버튼이 생깁니다.
   전부 되돌리려면 「전부 원래대로」 를 누릅니다.
3. 표준시간 상수는 공정마다 **미리보기**(OD914 × t9.3 × 12.802m 기준)와 **엑셀 행 번호**가 붙어 있어,
   지금 고친 값이 어느 항에 어떻게 들어가는지 바로 확인됩니다.
4. **「기준정보 내보내기」** 로 `.json` 한 장을 저장합니다. 기본값과 다른 항목만 담기고 한글 키를 씁니다.

```json
{
  "_포맷": "JCOE 시뮬레이터 기준정보",
  "설비대수": { "PACK": 2 },
  "전환시간": { "EndFacing": { "od": 0 } },
  "표준시간상수": { "Packing": { "base": 500 } }
}
```

5. 그 파일을 다른 사람이 **「불러오기」** 하면 똑같은 상태가 됩니다. 코드도 빌드도 필요 없습니다.

#### 안전장치

- 값을 안 건드리면 **엑셀 산출식과 완전히 동일**합니다 (`verify_formulas.js` 가 엑셀 원문으로 독립 검증).
- 설비 대수는 1~20 밖의 값을 무시합니다.
- 상수가 바뀌면 **확관 최적화 해는 자동으로 무효** 처리됩니다 (옛 조건의 해가 현재 값처럼 보이지 않도록).
- 회귀 검사 `verify_audit.js` 에 기준정보 항목(C1~C6)이 들어 있습니다 —
  반영·되돌리기·왕복 저장이 깨지면 바로 FAIL 납니다.

### 계획서 불러오기

기본 데이터는 2026년 3월 포항공장 조관계획서 기준 58오더 / 1,446본이지만, **다른 계획서 엑셀을 넣어 바로 돌릴 수 있습니다.**

2D는 「계획 실행」 탭 1단계, 3D는 상단 **계획서 불러오기** 버튼에서 파일을 끌어다 놓으면 됩니다.
`.xlsx` / `.xlsm` / `.xls` / `.csv` 를 읽습니다.

- **시트·헤더 행 자동 탐지** — 표지 시트나 제목 몇 줄이 위에 있어도 실제 헤더 행을 찾습니다. `JCOE` 가 들어간 시트를 우선 선택합니다
- **열 자동 인식** — `오더번호/제번/작번`, `외경/O.D`, `두께/육후/WT`, `길이/L`, `수량/본수/PCS`, `계획일/투입일자`, `납기/요청일` 등의 표기를 인식합니다. 못 찾으면 숫자 분포로 추정하고, 그래도 틀리면 화면에서 직접 지정할 수 있습니다
- **단위 자동 추정** — 외경 중앙값이 120 미만이면 inch, 길이 중앙값이 60 미만이면 m 로 판단해 mm 로 환산합니다. 수동 변경 가능
- **검증** — 필수값 누락·수량 0·범위 이탈 행은 건너뛰고 사유를 행 번호와 함께 표시합니다
- **필수 열은 외경·두께·길이·수량** 네 가지. 오더번호가 없으면 행 번호로, 계획 투입일이 없으면 시작일부터 순차 배치합니다
- 적용하면 공정 흐름·간트·병목·In/Out·최적화가 모두 새 데이터로 다시 계산됩니다. `orders.json` 내보내기와 기본 데이터 되돌리기도 지원합니다

형식 변형 테스트용 샘플은 `source/testdata/` 에 있고, `python3 source/tools/make_test_plans.py` 로 다시 만들 수 있습니다.

### 확률 변동 (Stochastic) 실행

기본은 **결정론**입니다 — 몇 번을 돌려도 결과가 같습니다. 「반복 실행」 탭에서 변동성을 켜면
**실행할 때마다 다른 결과**가 나옵니다.

| 요소 | 모델 |
|---|---|
| 작업시간 변동 | 표준시간 × 로그정규(평균 1, CV 기본 0.10) |
| 전환시간 변동 | 전환시간 × 로그정규(CV 기본 0.20) |

### 2-2. 확관 횟수 N — 정본은 `specs.py`

N 산출 근거가 두 자료에서 다르게 나타납니다. **2026-08-06 세아제강 회신으로 `specs.py` 가 정본으로 확정**되어
운영 모델 식을 기본값으로 씁니다. 엑셀 식은 대조용으로 「설정」 탭에서 전환할 수 있습니다.

| | #1호기 | #2호기 |
|---|---|---|
| **확관 최적화 운영 모델 `specs.py` (정본)** | `N = round(L / (step − (step≤150 ? 100 : 150)))` | `ceil((L−500)/step)+2`, 홀수면 +1 → **항상 짝수** |
| 「JCOE 공정 생산 표준 시간 분석」 (대조용) | `N = ceil(L / (step − 150))` | `ceil((L−500)/step)+2`, 짝수면 +1 → **항상 홀수** |

**2026-08-14 — 엑셀 #1호기 식의 근거를 찾았습니다.** 표준시간 엑셀 `Total Summary!S22` 에
**이미지로만** 붙어 있던 그림입니다(`source/data/evidence/`).

> 확관 Step Size = 다이 Size − 150mm (700mm 다이 → 550mm 를 HMI 레시피에 입력)
> `N = ROUNDUP( L / StepSize )` — 예시 **12,802mm / 24"×12.7t(다이 550mm) → 12,802/(550−150) = 33회**

즉 **#1호기는 두 자료가 사실상 같은 식**이고 올림(ROUNDUP)/사사오입(round)만 다릅니다 (N 차이 최대 1).
반면 **#2호기는 정반대**입니다 — 엑셀(`S23` 이미지 + 셀 메모)은 "N 은 항상 **홀수**",
정본 `specs.py` 는 "항상 **짝수**". 2026-08-06 회신에 따라 정본을 기본값으로 두고 재확인 요청 중입니다.

OD914 · t9.3 · L12.802m 기준으로 #1호기 엑셀 24회 vs 정본 **23회**, #2호기 엑셀 25회 vs 정본 **24회** 입니다.
| L(mm) | 다이 step(mm) | 분모 | N(엑셀 ROUNDUP) | N(정본 round) |
|---:|---:|---:|---:|---:|
| 12,802 | 700 | 550 | 24 | 23 |
| 12,802 | 460 | 310 | 42 | 41 |
| 12,802 | 300 | 150 | 86 | 85 |
| 12,000 | 110 | 10 | 1,200 | 1,200 |

두 식의 분모는 같고 **올림(엑셀) vs 사사오입(정본)** 만 다르므로 차이는 1회 이내입니다.
2026-08-14 전수 감사 전에는 소형 다이(step ≤ 150)에서 「끝단 150mm 이하면 −100」 규칙이
한 경로에만 적용돼 분모가 1mm 로 붕괴했고, 그때 두 식이 크게 벌어졌습니다 (지금은 해소).

실적 로그는 **스냅샷 poller** 라 한 간격이 여러 본을 담을 수 있어 `Δt / Δ누적` 으로 환산합니다.
문제는 그 다음입니다 — 완료 간격 분포는 **돌 때는 짧고 멈추면 아주 긴** 극단적인 오른쪽 꼬리 형태라,
**중위수를 쓰면 가동 중 페이스만 집어내고 대기를 통째로 버립니다.**

| 포장 PK113 추정치 | 값 |
|---|---:|
| 중위수 (가동 중 페이스) | 461 s |
| **처리량 기준 ΣΔt ÷ ΣΔ누적** | **1,028 s** |

2026-08-14 오전에 중위수 기준으로 「포장 표준시간이 실적보다 65% 느리다 → 산출식 재확인 필요」라고
보고했으나 **측정 오류**였습니다. 처리량 기준으로 다시 재면 전 설비에서 실적 ≥ 표준이 되고,
포장이 여유율 15% 로 가장 빡빡합니다. 세아제강에 드린 산출식 재확인 요청은 **철회**했습니다.

「실적 검증」 탭은 **실적 본당(처리량 기준)** 을 기본 지표로, **페이스(중위수)** 를 참고값으로 나눠 보여주고,
**여유율** 열로 병목을 판정합니다. 「실적 보정」 스위치는 실적이 표준보다 빠른 공정만 하향 보정하는 장치인데,
2026-08-14 실적 기준으로는 **보정 대상이 하나도 없습니다.**

## 3. 최적화 엔진

PPT「최적화 모델 구성」의 수식을 그대로 구현했습니다 — 병렬설비 + 순서의존 전환시간 스케줄링.

```
min  ①
s.t. ② Σ(m∈ℳ) z(j,m) = 1                      ∀j ∈ 𝒥        모든 작업은 정확히 한 설비에
     ③ z(j,m) = 0                              ∀(j,m) ∉ ℰ    적격집합 밖은 배정 불가
     ④ S(j) ≥ C(i) + s(ij) − M(1 − x(ij))      ∀m ∈ ℳ, ∀i,j ∈ 𝒥(m)
```

- 작업 `j` = 오더, `p(j,m)` = 수량 × 호기별 사이클타임, `s(i,j)` = 규격 변경 전환시간
- 목적함수 ①은 원자료에 비어 있어 **`w₁·Makespan + w₂·Σ전환시간 + w₃·호기부하편차`** 로 정의했습니다 (가중치는 화면에서 조정)
- 해 표현 = 전역 작업순서 `order[]` + SINGLE 작업의 호기 배정 `assign{}`
- 평가 = 전진 시뮬레이션. **BOTH 작업(L > 14.021m)은 #1·#2호기를 동시 점유**
- 규격 그룹핑 Greedy 초기해 → Simulated Annealing (swap / shift / 재배정), 24,000회 ≈ 1.5초
- 난수는 LCG 고정 시드(20260804) — **같은 입력이면 같은 해**가 나옵니다

### 배분 규칙별 결과 (정본 · 2근 실제 교대창 · R/B 는 열처리·배척 제품만)

| 배분 규칙 | Makespan | 확관 전환 | #1 / #2 (본) | 부하 편차 | 1위 병목 |
|---|---:|---:|---:|---:|---|
| **최단 가용 (Earliest Available)** | **24.4일** | 84.5h | 833 / 963 | 20.7h | JCOE 포장 99% |
| 전환 최소 (Setup-aware) | 25.3일 | 60.5h | 1,333 / 463 | 159.0h | JCOE 포장 95% |
| 최적화 엔진 | 25.1일 | **48.0h** | 881 / 915 | 20.3h | JCOE 포장 97% |

**해석 — 확관 최적화의 이득이 Makespan 으로 넘어오지 않습니다.**
최적화 엔진은 확관 전환시간을 84.5h → **48.0h 로 43% 줄이는 데 성공**하지만,
Makespan 은 24.4일 → 25.1일로 **오히려 늘어납니다.** 포장이 이미 99% 로 포화돼 있어
확관에서 아낀 시간이 그대로 포장 앞 대기로 옮겨갈 뿐이기 때문입니다.

즉 **지금 구성에서 확관 최적화는 지표를 개선하지만 납기를 앞당기지 못합니다.**
Makespan 을 줄이려면 **포장 라인 증설**이 먼저입니다 —
「기준정보」 탭에서 포장을 1대 → 2대로 바꾸면 24.4일 → **21.6일** 로 줄고 병목이 면취로 넘어갑니다.
그 상태에서 확관 최적화를 걸면 비로소 전환시간 절감이 Makespan 으로 이어집니다.

전환 최소 규칙이 부하 편차 159h 로 튀는 것은 같은 규격을 한 호기에 몰아주는 규칙의 성격상 당연합니다.

### 단위 해석 (재현 시 반드시 동일하게)

원자료의 "제품 Spec 길이"가 공정마다 단위가 다릅니다. 잘못 잡으면 결과가 수 배 어긋납니다.

| 공정 | 길이 단위 | 비고 |
|---|---|---|
| Press Bender, Gap Press | **m** | 예) `178 + 12.802/0.708 − 914/170 + X1(12회)×36 = 622.7s` |
| Edge Miller, Pre Bender, 용접, UT, 포장 | **mm** | |

그 밖의 해석:

- **확관 횟수 N** — 기본값은 정본(`specs.py`) 식입니다. #1호기 `round(L / (step−150))`(step ≤ 150 이면 `step−100`),
  #2호기 `ceil((L−500)/step)+2` 짝수 보정. 엑셀 「표준시간 분석」 식(항상 홀수)은 대조용 토글로 남겨 두었습니다 (§2-2).
  `step` 은 **호기별 다이표**(`dieSpec.M1/M2/RB`)에서 외경 ±5mm · 두께 최근접으로 조회
- **수압** 2차 압빼기·에어 벤트는 분 단위 (18" = 3분·2분, 36" 이상 = 5분·3분)
- **포장** 의 `250s × floor(지시량/10)` 은 10본마다 추가 검사 → 본별로 `seq % 10 == 0` 일 때 `+250s`
- **R/B 확관 Step Size = 다이 Size − 90mm** (2026-08-14 반영). 엑셀 `Expander(RB)!J4` 이미지 근거.
  `N = ceil(L / (다이−90))`, 소요 `234 + (N−2)×15`. 종전에는 −90 을 빠뜨려 확관 횟수를 과소 계상했습니다
  (OD914 t9.3 12.802m 기준 19 → **21회**, 489s → **519s**)
- 엑셀 `Expander(1호기)` 시트 107행은 `specs.py` 의 `die_specs_m1` 과 **전 행 일치**를 확인했습니다.
  `Expander(2호기)` 시트가 "비어 있다"고 본 것은 **내용이 이미지로 붙어 있었기 때문**입니다
  (2026-08-14 세아제강 지적). `tools/extract_images.py` 로 시트별 [값 / 이미지 / 메모] 를 먼저 확인합니다.
  다만 저희가 받은 20251231 판에는 1·2호기 시트 자체가 없어 `die_specs_m2` 68행 대조는 **원본 재요청 중**입니다
- **OD1219 `44t(250mm)` / `44t(700mm)`** 는 추출 오류가 아니라 **F/L(Full Length)이 다른 실물 다이 2개**입니다
  (같은 엑셀 RB 시트 셀 메모가 괄호 숫자를 F/L 로 표기). 현재는 엑셀 순서상 먼저인 250mm 를 씁니다 —
  어느 쪽을 거는지에 따라 확관 소요가 **1,767s vs 507s** 로 3.5배 갈립니다. 확인 요청 중

### 정본 대조

검증 명령은 §6 에 모아 두었습니다. 여기서는 **무엇을 무엇과 맞췄는지**만 적습니다.

**의도적으로 다르게 둔 것** — `specs.py` 는 외경에 ±5mm 하드 컷을 걸어, 다이표에 없는 외경을 만나면
두께를 보기도 전에 `UNKNOWN` 을 반환합니다. 그 결과 **서로 완전히 다른 규격 사이에도 셋업이 0초**가 됩니다.
시뮬레이터는 세아제강 방침(“가장 가까운 tool 에 매핑”)에 따라 **가장 가까운 외경의 공구로 폴백**하고,
화면에 `외경 457 → 다이표 610 (153mm 차)` 처럼 표시합니다. 드로바·헤드·다이 계층 판정이 정상 동작합니다.

### 왜 한 파일인가

2026-08-14 이전에는 `JCOE_Simulator.html` 과 `JCOE_3D.html` 두 파일이었습니다. 문제가 둘이었습니다.

1. 엔진(engine·flow·planload)과 xlsx 라이브러리 **880 KB 가 두 파일에 통째로 중복**
2. 더 중요하게 — **3D 가 자체 `runSim()` 으로 따로 시뮬을 돌렸습니다.**
   2D 에서 기준정보나 계획서를 바꿔도 3D 는 옛 값 그대로라 **두 화면이 서로 다른 답**을 보여줄 수 있었습니다.

이제 계산은 2D 앱에서 **한 번만** 하고, 3D 는 그 결과(`SIM`)를 `JCOE3D.update()` 로 받아 그리기만 합니다.

| | 종전 | 지금 |
|---|---:|---:|
| 파일 수 | 2개 | **1개** |
| 크기 | 1,171 + 1,716 = 2,887 KB | **1,895 KB** |
| 2D·3D 결과 일치 | 보장 안 됨 | 구조적으로 항상 일치 |

합치는 데 걸림돌은 두 가지였고, 이렇게 풀었습니다.

- `ui.js` 와 `scene3d.js` 가 `SIM`·`CFG`·`$`·`fmtT`·`loop`·`nodeState`·`logs` 를 각각 최상위에 선언
  → `scene3d.js` 전체를 `window.JCOE3D = (function(){ … })()` 로 감싸 **별도 스코프**로
- DOM id 가 33개 중 24개 충돌 (`btnPlay`·`seek`·`spd`·`cfgShifts` …)
  → 3D 쪽 `$()` 가 **`v3_` 접두어**를 붙이도록 (`$('gl')` → `<canvas id="v3_gl">`). 3D 마크업 이름은 그대로

WebGL 을 쓸 수 없는 PC 에서는 **3D 탭에만 안내가 뜨고 나머지 기능은 전부 정상 동작**합니다.

## 8. 감사 이력 — 이 저장소가 스스로를 어떻게 검사하는가

수치를 신뢰할 수 있는지가 이 프로젝트의 전부이므로, 두 차례 전수 감사를 돌리고
**찾은 결함을 전부 회귀 검사로 고정**했습니다. 상세는 [`CHANGELOG.md`](CHANGELOG.md) 에 있습니다.

| | 무엇을 | 결과 |
|---|---|---|
| **1차 (2026-08-14)** | 표준시간 산출식 20개를 엑셀 원문과 전수 대조 + 시뮬레이터 로직 | **계산 오류 10건** 정정. 골격·상수는 전부 일치했고 결함은 **조건 분기·빠진 항·룩업 경계**에 있었음 |
| **2차 (2026-08-14)** | UI · 3D · 엔진 기준정보 레이어 · 데이터 로더를 병렬 감사 | **결함 25건** 정정. 화면에서 값이 사라지는 문제, 데이터 로더의 열 오인식, 프로토타입 오염·XSS 포함 |

1차에서 가장 컸던 것 — Gap Press 가 실제의 **2~4배**로 계산되고 있었습니다.
엑셀 산출식의 대괄호 밖 `×2` 가 「X70 이상」 조건인데 무조건 곱한 뒤 X70 에 또 곱했고,
게다가 투입 조건(t>25)과 고강도 판정 기준(t>25)이 같아 **투입 제품이 전부 X70 으로 판정**되고 있었습니다.

2차에서 가장 컸던 것 — 계획서의 **외경 열이 통째로 잘못 잡히는** 경우가 있었습니다.
열 별칭 `o.d` 가 헤더 `MODEL` 에 부분일치하면 바로 옆의 정확한 `OD` 열이 영영 이기지 못해,
모델명(800·1200)이 외경으로 들어갔습니다.

**두 감사 모두 「결론을 뒤집지는 않았습니다」** — 포장이 1위 병목이라는 §2-3 의 진단은
정정 후에도 그대로이고, 오히려 더 뚜렷해졌습니다(96.9% → 99.3%).
